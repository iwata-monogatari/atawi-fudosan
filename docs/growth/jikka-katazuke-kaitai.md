# 片付けと解体前の相談特集の運用

ATAWI FUDOSAN内で、片付けや解体の支出前に相談を受け、物件ごとの比較材料を整理する。問い合わせ数と実際の売却依頼は分けて記録する。

## 公開ページ

- 特集 `/jikka/katazuke-kaitai/`
- 比較資料の構成見本 `/jikka/katazuke-kaitai/hikaku/`
- 受付 `/karte/` → `/api/karte-apply` → 既存Resend通知
- 関連記事5本は既存の拡張子なしURLを維持。トップ、実家じまい、施設入居後の家、関連する無料診断から案内する。

## 受付後の対応

1. 既存の受付メールを確認し、希望した返信方法で対応する。物件所在地、所有者との関係、本人・家族の意向、困りごとを確認し、回答の目安を伝える。
2. 机上の価格目安、確認できた事実、未確認のことを分ける。費用が未確認なら0円にしない。
3. 古家のまま、片付け後、解体後の案を比較する。残置物処分と解体の費用の重複、見積りの範囲・有効期間、税・借入残高など未反映の支出を明記する。
4. 必要な現地確認、見積り、専門家への確認を案内する。実作業や追加調査の内容・費用は依頼前に確認する。
5. 売却を希望する場合に、詳しい査定・販売条件・媒介契約の説明へ進む。フォーム送信を媒介契約や成約として扱わない。

写真・書類は初回受付後、必要なものと送付方法を既存の連絡経路で案内する。比較資料は担当者が物件ごとに作成する。自動査定や自動見積りは実装していない。

## 計測と記録

既存の計測基盤へ次のイベントを送る。メタデータは固定の特集名・悩み分類・記事の識別子だけ。住所、氏名、連絡先、相談メモ、自由なURLパラメーターをイベントに含めない。内部確認・自動操作・localhost・Pagesプレビューは既存ヘルパーで除外する。

| イベント | 意味 |
| --- | --- |
| `jikka_special_view` | 特集の閲覧 |
| `jikka_special_sample_view` | 比較資料の閲覧 |
| `jikka_special_sample_click` | 比較資料へのリンク操作 |
| `jikka_special_consult_click` | 特集から既存フォームへの操作 |
| `jikka_special_form_start` | 特集経由のフォーム入力開始 |
| `jikka_special_application_success` | APIが通知サービスへの受付成功を返した申込み |
| `jikka_special_submit_error` | 申込みの送信失敗 |

成功はメールの受信箱への到達や担当者の対応完了までは意味しない。フォーム全体の既存コンバージョンはthanksページが担当するので、特集成功イベントと合算しない。遷移直前イベントはネットワーク状態によって欠けうるため、実受付は通知メールと突き合わせる。LINE・電話はクリック数を受付数として扱わない。

記事の引継ぎはURLの固定キー`entry`と`concern`を使う。ブラウザーをまたぐ追跡や新しい個人識別子は追加しない。通常のフォーム流入には前回の特集情報を残さない。

管理者は既存の非公開案件管理で、同一物件・同一相談者をまとめて、受付日、入口、物件特定、現地相談、売却相談、媒介契約を記録する。個人情報をこのリポジトリや公開の解析画面へ保存しない。90日の仮目標は有効相談6件、現地相談3件、媒介契約1件で、予測値ではない。月次で入口別の実受付と進捗を確認する。

## 更新と公開

この特集と関連記事5本はHTMLを直接管理する。旧記事生成ツールによる一括再生成は今回の本文を上書きするため、差分を確認する。診断を再生成するときも「価格は出ません」という旧案内を復活させない。

公開前は `node --test tests/*.test.cjs`、`node _tools/check-public-facts.mjs`、`git diff --check` を実行する。特集→比較資料→フォームで入口と悩みが保たれること、320pxの幅で横にはみ出さないことを確認する。テスト送信は通知サービスを模擬した環境で行う。本番へダミー相談を送らない。

GitHubのmainへの反映後、Cloudflare Pagesの成功を確認し、独自ドメインで内容を確認する。公開日が変わった場合は、新規ページと今回更新したページのサイトマップ日付・更新履歴を合わせる。戻す場合は本変更のコミットをrevertし、mainへ反映する。既存フォームや通知先の設定を巻き戻し操作で消さない。
